Platform reference

What the platform actually gives you.

GitHub Pages is a static file host with a Jekyll build attached. Almost every “can Pages do X?” question resolves to one of three answers: yes because the browser does it, yes because a build step does it, or no because it needs a server. This page sorts them out.

Build pipelines

Three ways to publish

The choice of pipeline decides which tools you can use. It is the single most consequential decision in a Pages setup, and it is reversible.

1. Plain static files

Commit HTML, CSS, and JS; Pages serves them. Add .nojekyll to skip the build entirely — required the moment any directory starts with an underscore, which is why Next.js output (_next/) silently breaks without it.

This repository uses this mode.

2. Built-in Jekyll

Push Markdown and Pages builds it. No workflow file, no build minutes. The cost is the plugin allowlist: roughly sixteen plugins are permitted and Gemfile additions are ignored.

Copy-paste starter: examples/jekyll/ in this repository.

3. GitHub Actions

Build with anything — Astro, Eleventy, Hugo, Vite, a static Next export, or Jekyll with unrestricted plugins — then publish the output with actions/deploy-pages.

Workflows: .github/workflows/ in this repository.

Comparison of the three publishing pipelines
Pipeline Build minutes Tooling Best for
Static files None used Whatever runs in the browser Hand-written sites, prebuilt output committed to the repo
Built-in Jekyll None used Allowlist only Markdown blogs and docs with zero configuration
GitHub Actions Consumes quota Anything Modern SSGs, custom pipelines, unrestricted plugins

Capability matrix

Can Pages do it?

Every row marked Yes is demonstrated live in this repository, not asserted. Follow the link and watch it work.

Third-party glue

Where a backend is unavoidable

Two things genuinely need a server: accepting input and storing it. The static answer is to borrow someone else’s. These snippets are shown rather than wired up — both need an account and an endpoint of your own, and this page’s form-action 'none' policy would block a live submission anyway.

Forms

Point a normal <form> at a form-relay service. No JavaScript is required, and it degrades gracefully. 

<form action="https://formspree.io/f/YOUR_ID" method="POST">
  <label for="email">Email</label>
  <input id="email" type="email" name="email" required />

  <label for="message">Message</label>
  <textarea id="message" name="message" required></textarea>

  <button type="submit">Send</button>
</form>

Remember to relax form-action in your CSP to the relay’s origin.

Comments

Giscus stores each thread as a GitHub Discussion, so a repo-hosted blog keeps its comments in the same repository as its posts — no third-party database. 

<script src="https://giscus.app/client.js"
  data-repo="OWNER/REPO"
  data-repo-id="YOUR_REPO_ID"
  data-category="Announcements"
  data-category-id="YOUR_CATEGORY_ID"
  data-mapping="pathname"
  data-theme="preferred_color_scheme"
  crossorigin="anonymous"
  async>
</script>

Requires Discussions enabled on the repo and the giscus app installed.

Hard limits

The published quotas

These are soft in the sense that GitHub contacts you rather than cutting you off, but they are the documented ceilings. Check the official docs before designing around a number — they do change.

Published GitHub Pages limits
Limit Value What it means in practice
Published site size 1 GB Generous for a site; restrictive if you are hosting video or large datasets.
Bandwidth 100 GB / month A soft limit. Sustained overage earns an email, not an outage.
Builds 10 per hour Applies to the built-in Jekyll pipeline. Actions-based deploys are governed by your Actions quota instead.
Deployment timeout 10 minutes A build that exceeds it fails. Large sites should prebuild in Actions.
Intended use Not for commerce The terms exclude running an online business or a commercial transaction site.

Gotchas

The things that actually break

Project pages have a path prefix

A repository named <owner>.github.io serves at the domain root. Every other repository serves at /<repo>/, so every root-absolute URL (/assets/app.css) breaks.

This repository is a live example. It is named harveyciphers.github.io but owned by itsharveyciphersbase, and the two do not match — so it is a project page served from a subpath, not a user page. Everything here uses relative URLs for exactly that reason.

Underscores disappear

Without .nojekyll, the Jekyll build strips directories beginning with an underscore. Next.js emits _next/, so the site deploys successfully and then loads nothing at all — a uniquely confusing failure.

The CNAME file gets overwritten

Setting a custom domain in the repository settings commits a CNAME file. A deploy that publishes a build directory without it silently drops your domain. Copy it into the output, or set it in the workflow.

URLs are case sensitive

Pages serves from a case-sensitive filesystem. A link to /About.html for a file named about.html works on a Windows or macOS dev machine and 404s in production.

Service workers outlive your patience

A cached service worker keeps serving the old site after you deploy. Version your caches, clean up on activate, and give visitors an explicit update prompt — the pattern in sw.js and modules/pwa.js here.

Everything is public

A private repository can publish a public Pages site. Nothing in the repo is protected by the repo being private: API keys in a bundle, draft posts, and commented-out content all ship.
